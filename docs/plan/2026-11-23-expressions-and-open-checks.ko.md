## 2. 측정 방법

- `tests/expression_probe.cpp`(측정 도구, 테스트 아님): 생활 한자·이모티콘·이모지·문장 부호·감정 표현어 59줄을 실제 글꼴로 그려 PaddleOCR(`jpn+eng+kor`)로 읽는다. 일본어는 Yu Gothic·Meiryo·MS Gothic, 한국어 Malgun Gothic, 중국어 Microsoft YaHei, 영어 Segoe UI. 글꼴마다 "흰 바탕 검은 글씨"와 "어두운 바탕에 외곽선 있는 굵은 흰 글씨(게임식)" 두 가지로, 모두 256번 읽는다. 읽은 글, 가장 낮은 글자 확신도, 앱의 규칙(문장 끝 판단, 번역할 부분 나누기)을 JSON으로 남긴다. `--deepl`이면 원문 그대로를 앱과 같은 방식으로 나눠 실제 DeepL에 보낸다.

## 3. 결과 — 표현 분류 (X1~X7)

### 3.1 고치기 전에 찾은 문제

| 무엇 | 고치기 전 | 원인 |
|---|---|---|
| 이모지 | 30번 중 한 번도 읽지 못함. 대부분 빠지지만 7번은 엉뚱한 글자가 붙음: `おめでとう楽`(0.12), `おめでとうご`(0.24), `おめでとう送`(0.27), `悲しい🎯`(0.41), `最高！自` 3번(0.86~0.93) | 모델 사전에 이모지가 없음 |
| `♪` | 6번 중 4번 `」`로 읽음(0.50~0.56) | 모양이 닮음 |
| 얼굴 문자 속 `^` | `(^_^)` → `(ヘ_^)`, `(ヘ_へ)`, `(^^)` → `(へへ)` | `^`를 `へ`로 읽음 |
| 한국어 `^^` | `고마워요^^` → `고마워요ㅅㅅ`(뜻이 바뀜) | 한국어 모델이 `^`를 `ㅅ`으로 읽음 |
| 한국어 속 한자 | `학교(學校)에 갑니다` → `학교()에 갑니다` | 한국어 모델에 한자가 없음. 중국어·일본어 모델은 `(學校)`를 읽음 |
| 문장 끝 판단 | `♡` `☆` `⁉` `・・・` `ｗｗｗ` `orz` `ㅋㅋㅋ` `ㅠㅠ` `^^` `あはは` `666` `:D` `<3`로 끝나는 줄을 "안 끝난 문장"으로 봄 | 끝 글자 목록에 문장 부호만 있었음 |

이 밖에 확인한 것:

- 생활 한자는 58번 중 48번 정확했다. 틀린 것은 대부분 끝의 `。` `！`가 빠진 것이었고(번역에는 영향이 거의 없고, 끝 판단이 늦어질 뿐), 그 밖에는 `っ` → `つ` 한 번이었다.
- `(T_T)`, `orz`, `（笑）`, `ｗｗｗ`, `ㅋㅋㅋ`, `ㅎㅎ`, `(╥﹏╥)`(→ `(π…π)`), `:)` `<3`은 대체로 읽었다. `＼(^o^)／`, `(´・ω・`)`는 글꼴에 따라 일부만 읽는다.
- `……`만 있는 줄은 읽지 못하거나(`.·.·.`, `000000`) 걸러진다. 번역할 글자가 없어서 요청은 가지 않는다.
- `아… 그렇구나`는 `…`와 띄어쓰기가 빠진 `아그렇구나`로 읽힌다(한국어 모델). 한국어 줄은 한국어로 번역할 때 보내지 않으므로 영향이 작다.
- 번역할 부분 나누기(X6): 일본어·한국어·중국어 줄에 붙은 얼굴 문자·이모지는 문장과 함께 DeepL로 가고, 띄어 쓴 영어 이모티콘(`:)` `<3` `:(`, 이모지)은 번역하지 않고 그대로 붙인다.

### 3.2 실제 DeepL(X7)

원문 그대로 54줄, 417자를 보냈다(사용량 222,073 → 222,484자). 한 요청은 620~770ms.

- 얼굴 문자·이모지·`♪` `♡` `☆` `⁉`는 모두 그대로 돌아온다: `ありがとう(^_^)` → `고마워요(^_^)`, `おめでとう🎉` → `축하해요🎉`, `ふふっ♪` → `후후♪`.
- 그 나라 표현은 바꿔 준다: `ｗｗｗ` → `ㅋㅋㅋ`, `（笑）` → `(웃음)`, `666` → `대박`, `LOL` → `ㅋㅋ`, 한국어 → 일본어에서 `ㅋㅋㅋ` → `（笑）`, `ㅠㅠ` → `（涙）`.
- 그래서 얼굴 문자·이모지를 문장과 함께 보내는 지금 방식이 맞다. 따로 떼어 두면 `ｗｗｗ` 같은 표현이 바뀌지 않는다.

## 4. 결과 — 남은 검증 (U1~U5)

### 4.1 U1 실제 DeepL 자동 번역

`scene_probe --deepl`로 가짜 게임 3장면(정지, 화살표 위아래, 한 글자씩)을 실제 DeepL로 돌렸다. 216자를 썼다(222,484 → 222,700).

| 장면 | 줄 | 요청 | 보낸 글자 = 줄 글자 | 자막까지 평균 (최대) | 같은 장면, 가짜 서버 |
|---|---|---|---|---|---|
| 정지 | 4 | 4 | 46 = 46 | 1.11초 (1.16) | 0.47초 |
| 화살표 위아래 | 4 | 4 | 46 = 46 | 1.18초 (1.66)* | 0.44초 |
| 한 글자씩 | 4 | 4 | 78 = 78 | 1.18초 (1.56)* | 0.41초 |

\* 첫 실행은 측정 도구가 연결을 미리 열지 않아(테스트 모드는 DeepL에 미리 연결하지 않는다) 첫 줄이 0.6초 더 걸렸다. 앱처럼 미리 열게 고친 뒤 정지 장면은 첫 줄도 1.16초였다.

- 실제 DeepL에서도 **요청 수 = 줄 수, 보낸 글자 = 줄 글자**였다. 같은 줄을 다시 번역하지 않는다.
- 자막까지 약 1.1초 중 0.4초는 읽기, 0.7초는 DeepL 왕복이다. DeepL의 `model_type`은 기본값이 이미 `latency_optimized`라서 요청으로 더 줄일 수 없다.

### 4.2 U2 확신도 기준 0.9

256번 읽기에서 **바르게 읽은 줄의 46%가 0.9 미만 글자를 가졌다.** 대부분 문장 부호다(`？` 0.70, `！` 0.74). 움직이는 화면이면 이런 줄마다 0.4초 기다려 한 번 더 읽는다. 반짝임이 만든 오독(`今白` 0.53, `まじょう` 0.63)은 글자에서 생긴다.

| 기준 | 바른 줄을 의심함 | 틀린 줄을 의심함 |
|---|---|---|
| 모든 글자 < 0.9 (전) | 79/172 (46%) | 38/84 (45%) |
| 글자·숫자만 < 0.9 (후) | **17/172 (10%)** | 18/84 (21%) |

틀린 줄의 대부분은 글꼴 때문에 늘 같게 틀리므로 다음 화면을 읽어도 같다. 의심은 움직임 때문에 생긴 오독에만 쓸모가 있다. 그래서 `doubtful()`이 글자·숫자의 확신도만 보게 했다(`LineInfo::lowestLetter`). 17장면을 다시 재 보니 모든 장면에서 요청 = 줄, 반짝임 장면 3번을 더 재도 요청 = 줄이었다.

### 4.3 U3 오래 켜 두기

`scene_probe long`: 가장 바쁜 화면(깜빡이는 화살표, 움직이는 배경, 반짝임)에 대사 60줄을 10초씩, 10분 동안 띄웠다. 기억으로 답하지 않도록 줄마다 앞에 번호를 붙였다(`12回目、…`). 메모리는 이 프로세스의 사용 중 메모리(private bytes), CPU는 한 코어 기준이며 가짜 게임의 초당 30번 그리기를 포함한다.

| | 1차 (조각 기억 전) | 2차 (조각 기억 후, 5.2절) |
|---|---|---|
| 자막 표시 | 45줄 모두 (46번째 줄부터는 다른 창이 영역을 덮어 제외) | **60줄 모두** |
| 메모리, 6번째 줄 이후 | 400.5~406.9MB | 399.4~405.5MB, 마지막 400.7MB |
| CPU | 9.5~10.1% | 8.5~11.6% |
| 자막까지 평균 (최대) | 0.70초 (1.96) | 0.69초 (2.25) |
| 요청 | 앞 45줄에 46번(같은 조각 중복 2번) | **60줄에 6번**(88자, 줄 글자 981) |

- 메모리는 처음 몇 줄에 384 → 400MB로 오른 뒤 10분 동안 늘지 않았다. 누수는 보이지 않는다.
- 1차 끝에 다른 창(여러 줄의 긴 글)이 영역을 덮자 메모리가 44MB 늘었다. 더 큰 글을 읽을 때 ONNX Runtime이 작업 메모리를 늘린 것으로 보인다. 그 창의 글은 결과 파일에서 지웠다.
- 2차의 6번은 문장 4개와, 반짝임 때문에 다르게 읽힌 조각 2개(`・明日は…`, 끝 `。` 빠짐)다. 번호만 다른 56줄은 요청 없이 조각 기억으로 표시됐다.
- 1시간 실행(P-12 C-06)은 아직 하지 않았다.

### 4.4 U4 Android

에뮬레이터 `Medium_Phone`(Android 15, API 35, 창 있음)에서 프로토타입을 다시 빌드하고(Android Studio JBR 25.0.4) 계측 테스트를 돌렸다.

- **실제 번역**: 새 테스트 `realTranslationWhenAKeyIsGiven`이 앱의 흐름(공유 이미지 → 자르기 → ML Kit 일본어 OCR → DeepL) 그대로 실제 DeepL을 불렀다. `今日はいい天気です。` → `오늘은 날씨가 좋습니다.`, OCR 3,870ms(첫 실행), 번역 987ms, 10자.
- 키는 측정 스크립트가 Windows 자격 증명 저장소에서 읽어 계측 인자(`-e deeplKey`)로만 넘겼다. 앱에는 메모리로만 넣고 저장하지 않으며, 로그와 결과 파일에 남기지 않는다. 키를 주지 않으면 이 테스트는 건너뛴다.
- 키 없이 전체 4개: 3개 통과, 1개(실제 번역) 건너뜀. 처음에는 "백그라운드로 가면 진행 중인 읽기를 취소"를 800ms 안에 확인하는 부분이 실패했다. 창 있는 에뮬레이터는 `onStop`을 그보다 늦게 불렀다(예전 검증은 창 없는 에뮬레이터). 정해진 800ms 대신 5초 안에 취소되기를 기다리게 고쳤다.
- 실기기는 연결된 기기가 없어 여전히 확인하지 못했다(P-15).

### 4.5 U5 실제 게임·모니터 2대·코드 서명

## 5. 함께 고친 것

### 5.1 타자기 줄 절반 전송

전체 테스트를 반복하다 `longTypewriterSentenceIsSentOnce`가 가끔(약 4번에 1번) 실패하는 것을 찾았다. 고치기 전 코드에서도 같은 비율로 실패했다.

- 3초 넘게 찍히는 줄은 찍히는 도중 한 번 읽는다(P-24). 그 읽기는 끝나지 않은 문장이라 기다리게 둔다.
- 기다리는 줄은 "윤곽이 멈춘 지 225ms, 기다린 지 0.8초"가 되면 보낸다. 감지기의 마지막 읽기는 "픽셀이 멈춘 지 225ms"에 한다. 윤곽은 픽셀보다 먼저 멈추므로, 기다리던 절반(`…本当にそ`)이 마지막 읽기보다 한 번 먼저 나갈 수 있었다. 나머지(`う思います。`)는 앞부분 재사용으로 따로 나가서 요청이 2번이 됐다. 글자 수는 같지만 요청이 하나 늘고 잠깐 반쪽 번역이 보인다.
- 고침: 찍히는 도중 읽은 줄 뒤에 감지기가 한 번 더 읽어야 할 때(`ChangeDetector::readOwed()`)는 기다리는 줄을 보내지 않는다. 그 뒤로 22번 반복해 모두 통과했다.

### 5.2 보내지 않는 부분만 다른 줄: 조각 기억

10분 장면(4.3)에서 줄마다 앞에 번호를 붙였다(`12回目、今日はいい天気ですね。`). 번호는 번역하지 않고 그대로 두므로 DeepL에는 `回目、今日はいい天気ですね。`만 간다. 그런데 최근 200줄 기억은 줄 전체(번호 포함)를 열쇠로 써서, 번호만 다른 줄이나 번호를 한 번 잘못 읽은 같은 줄(`9回目` → `19回目`)은 같은 조각을 다시 보냈다(앞 45줄에서 2번).

- 고침: 보낸 조각과 번역을 따로 기억한다(`pieceCache_`, 최근 200개, 메모리에만). 보낼 조각이 모두 기억에 있으면 요청 없이 그 번역으로 보여 주고 "기억해 둔 번역"이라고 표시한다. 앞부분을 문맥으로 함께 보낸 뒷부분(P-38)은 문맥에 따라 번역이 달라서 기억하지 않는다.
- 테스트: `13回目、今日はいい天気です。`는 `12回目、…`의 조각 번역으로 요청 없이 표시되고, 다른 문장은 그대로 요청한다.

### 5.3 화면 테스트가 가끔 실패하는 것

`autoTranslateReadsEachNewLineOnce`(Tesseract)도 다른 화면 테스트 바로 뒤에 돌리면 가끔 같은 줄을 한 번 더 읽는다. 그 순간 화면 영역의 픽셀이 실제로 움직였다(`moving 1`). 고치기 전 코드에서도 같은 비율이고, 혼자 돌리면 10번 모두 통과한다. 실제 화면을 읽는 테스트라 PC에서 다른 창이 움직이면 영향을 받는다(장면 측정 한 번에서는 다른 창의 글자가 영역에 들어와 함께 보내졌다). 원인을 더 좁히지 못해 테스트 실패 메시지에 읽은 시각과 움직임 여부를 남기게 했다. 장면 측정 도구도 가짜 게임의 글이 아닌 것은 내용 없이 `(다른 글)`로만 적게 바꿨다(사용자 화면의 글을 파일에 남기지 않도록).
