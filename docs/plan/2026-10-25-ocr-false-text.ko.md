# 특수기호·빈 대사창 오인식 줄이기 — 계획과 결과

작성 2026-10-25 · 백로그 P-01, P-02 · 브랜치 `ocr-accuracy-foreign-only` · 기준 커밋 `af75585`

## 1. 현재 상태

| 항목 | 지금 동작 | 근거 | 문제 |
|---|---|---|---|
| 기호만 있는 줄 | PaddleOCR이 비슷한 글자로 바꿔 읽음 (`○` → `O`, `「」` → `J]`) | QA 540회 측정: 기호만 있는 이미지 72개 중 33개에서 글자 생김, 25개는 번역 조각 발생 | 엉뚱한 짧은 자막, 불필요한 DeepL 전송 |
| 기호 + 글자 | `♪ Hello ♪` → `s Hello s` | 같은 측정 | 기호가 글자가 되어 문장 전체가 바뀌어 전송 |
| UI 구분선 | `HP \| MP \| SP` → `HPIMPISP` (12개 중 6개) | 같은 측정, `src/ocr_service.cpp` `cleanText` | `\|`→`I` 바꾸기가 Tesseract 보정인데 PaddleOCR 결과에도 적용됨 |
| 숫자 옆 한글 | `Lv.10` → `1이` (12개 중 11개) | 같은 측정 | 숫자가 한글로 바뀜 |
| 거의 빈 대사창 | 액자 `I ,`, 테두리 `リー`, 잡음 `し` | QA 수정본 재검증, REPORT A-05 frame FAIL | 빈 대사창마다 가짜 자막 |
| 줄 신뢰도 | PaddleOCR이 줄·글자별 확률을 계산하지만 거르는 데 쓰지 않음 | `src/paddle_ocr.cpp` `decode`, `PaddleOcr::read` | — |
| 기존 결정 | 신뢰도 하한·짧은 글자 필터를 넣지 않음 | [DECISIONS](DECISIONS.md) 2026-10-01 | 정상 1–3글자 대사(`はい`, `OK`)를 지키기 위한 결정. 이번 변경은 이 대사들이 그대로 남는 것을 측정으로 보여야 함 |

## 2. 목표와 범위

목표: 기호·테두리·잡음을 글자로 바꿔 읽어 번역 요청이 생기는 경우를 줄이되, 정상 짧은 대사와 일반 문장 정확도는 그대로 둔다.

| ID | 바꿀 것 | 종류 |
|---|---|---|
| G1 | 진단: PaddleOCR 줄별 글자·줄 신뢰도·가장 낮은 글자 확률을 CLI JSON에 남김 (원문은 이미 출력하던 값) | 신규 |
| G2 | `\|`→`I` 바꾸기를 Tesseract 결과에만 적용 | 수정 |
| G3 | 측정으로 정한 기준에 따라, 확신 없는 짧은 줄과 확신 없는 단독 글자를 버림 | 신규 |
| G4 | 숫자 사이·뒤의 확신 없는 한글 `이`, 라틴 `O`·`o` 처리 (측정 후 결정) | 보류 가능 |

범위 밖: 기호를 기호로 읽는 새 모델(인식 사전에 기호가 없음), Tesseract 경로의 신뢰도 기준 변경(이번 측정에서 비중이 작으면 다음으로).

## 3. 설계

- `PaddleRecognizer::decode`가 글자별 확률을 함께 돌려주고, `PaddleOcr::Result`에 줄 목록(글자, 줄 신뢰도, 글자별 확률)을 담는다.
- 거르기는 `PaddleOcr::read`에서 줄을 합치기 전에 한다. 버린 줄 수를 결과에 남겨 CLI JSON에서 볼 수 있게 한다.
- 모든 줄이 걸러지면 빈 결과가 되고, 기존 흐름대로 Tesseract가 다시 읽는다. Tesseract도 같은 잡음을 읽을 수 있으므로 측정에서 함께 본다.
- 기준값(줄 길이, 신뢰도 하한)은 코드에 상수로 두고, 근거 측정값을 주석과 이 문서에 남긴다.

## 6. 결과 (2026-10-25)

### 바꾼 것

| 규칙 | 내용 | 위치 |
|---|---|---|
| G1 진단 | PaddleOCR 줄마다 글자·줄 신뢰도·글자별 확률·사용 모델, 검출 모델이 찾은 줄 수, Tesseract 신뢰도를 `ocr_benchmark` 결과(v2)에 기록 | `PaddleOcr::Result`, `OcrService::paddleDetails()`, `tests/ocr_benchmark.cpp` |
| G2 | `\|`→`I` 바꾸기를 Tesseract 결과에만 적용 | `OcrService::cleanText(text, fromTesseract)` |
| 규칙 1 (짧은 줄) | 글자·숫자 3개 이하인 줄은 가장 확신하는 글자가 0.85 미만이면 버림 | `PaddleOcr::filterLine` |
| 규칙 2 (양끝 한 글자) | 띄어쓰기로 떨어진 양끝의 라틴·한글·가나·숫자 한 글자는 확률 0.5 미만이면 버림. 힌디어·아랍어는 제외 | 같은 함수 |
| 규칙 A | 검출 모델이 글자 줄을 0개 찾았거나 찾은 줄이 모두 규칙 1로 버려지면 Tesseract로 넘기지 않고 빈 결과 | `OcrService::runPaddle` |
| 규칙 B | Tesseract 결과의 신뢰도가 30 미만이면 빈 결과 | `OcrService::isUnsureReading` |

빈 결과는 공통 코어에서 `ST_EMPTY`가 되어 번역 요청을 만들지 않는다. 자동 번역 중이면 이전 자막을 숨기고 다음 대사를 기다린다(기존 단색 빈 화면과 같은 경로).

### 기준값을 정한 근거 (진단 측정)

| 묶음 | 줄에서 가장 확신하는 글자의 확률 |
|---|---|
| 기호를 글자로 읽은 짧은 줄 20종 (`O`, `J]`, `ㅁ`, `[jrJ[]` …) | 0.14 – 0.78 |
| 정상 짧은 대사 (`はい`, `いいえ`, `OK`, `네`, `응`, `아!` …) | 0.917 – 1.0 |
| 정상 문장 글자 전체 (672·168장, 14,989자) | 하위 1%가 0.648 (주로 힌디어·아랍어) → 확률로 일괄 거르면 안 됨 |

| Tesseract 결과 | 신뢰도 |
|---|---|
| 빈 화면에서 지어낸 글자 | 13.1, 27.9, 33.0, 50.4 |
| 정상 짧은 대사를 맞게 읽은 최저값 | 36.1 (`응`), 다음 69.1 |
| 정상 베트남어 문장 최저값 | 50.2 |

처음 안은 "Tesseract 3글자 이하 + 신뢰도 60 미만이면 버림"이었다. 그러나 맞게 읽은 `응`(36.1)까지 버리게 되어 [결정 2026-10-01](DECISIONS.md)과 충돌했다. 그래서 겹치지 않는 30 미만으로 좁혔다.

- `paddle_ocr` `filterLineDropsMisreadSymbolsOnly`: 측정된 확률값으로 규칙 1·2의 경계 확인 (힌디어·아랍어 제외 포함)
- `local_checks` `falseTextIsNotRead` 10행: 측정에서 결정적이었던 이미지 9장(`tests/fixtures/ocr/false-text/`)을 실제 엔진으로 읽음. 빈 액자·테두리·잡음 → 빈 결과, `♪ Hello ♪` → `Hello`, 확률이 가장 낮았던 정상 대사 `いいえ`·`네`, Tesseract `응`(36.1) → 그대로

### 남은 오인식 (백로그로)

| 경우 | 원인 | 백로그 |

### 개발 중 발견한 것

- **Smart App Control**(이 PC에서 켜짐)이 서명 없는 새 실행 파일을 빌드마다(해시마다) 다시 판정한다. `subtitle_cli.exe`는 모든 빌드에서 막혔고 `ocr_benchmark.exe`는 막혔다가 다시 빌드한 뒤 통과했다. 끄면 Windows를 다시 설치하기 전까지 다시 켤 수 없으므로 끄지 않았다. 측정 도구는 `ocr_benchmark`로 바꿨다(같은 `OcrService`, 네트워크 없음).
- 측정 채점에서 NFKC 정규화가 로마 숫자 `Ⅲ`을 라틴 `III`으로 바꿔 "글자 생김"으로 잘못 세던 것을 원문 기준으로 고쳤다.
- 전체 CTest 첫 실행에서 `autoTranslateReadsEachNewLineOnce`가 한 번 실패했다. 이때 UI 그룹 시간이 평소 25초 대신 101초였다. 이후 OCR 변경 직전 빌드(`af75585`)와 번갈아 5회씩 돌렸을 때 둘 다 5/5 통과했고, 전체 재실행도 통과했다. 새 실행 파일 첫 실행 때의 보안 검사로 느려진 것으로 **추정**한다. 다시 생기면 원인을 볼 수 있도록 실패 메시지에 읽은 원문·엔진·신뢰도·상태를 남기게 했다.
