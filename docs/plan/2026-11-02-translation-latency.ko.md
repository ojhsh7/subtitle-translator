# 번역이 화면에 뜨기까지의 시간 줄이기 — 계획과 결과

작성 2026-11-02 · 백로그 P-31 · 브랜치 `ocr-accuracy-foreign-only` · 기준 커밋 `69efac6`

요청: "번역을 더 빠르게 바로 보고 싶다. 번역 속도와 화면 출력을 빠르게 하는 계획을 세우고, 개발 환경을 고려한 뒤 가능한 빠르게."

## 1. 현재 상태 (자동 번역, 대사 한 줄)

| 단계 | 지금 | 근거 |
|---|---|---|
| 대사가 바뀐 걸 알아챔 | 0.4초마다 캡처, 평균 0.2초 늦게 알아챔 | `autoTimer_` 400ms |
| 글자 출력이 멈췄는지 기다림 | 같은 화면이 2번 연속(0.8초) | `ChangeDetector::StableTicks` |
| OCR | 기본 설정 대사창 약 0.1초 | P-26 |
| DeepL 요청 | 연결이 열려 있으면 0.25초 + 처리 시간, 끊겨 있으면 **0.5초 더** | 아래 측정 |
| 화면 표시 | 수 ms | `SubtitleOverlay::showText` |
| **합계** | 약 1.6–2.1초 | QA C-03(OCR까지) 1.19초 + DeepL |

반복되는 대사(메뉴, 다시 나오는 대사, 선택지)도 매번 DeepL에 보낸다. 직전 1줄만 기억한다.

## 2. 개발·실행 환경 측정 (2026-11-02, 이 PC)

| 측정 | 값 | 방법 |
|---|---|---|
| DeepL 서버까지 왕복 | **약 250ms** (서버 194.124.204.71, 유럽) | `curl`, 키 없이 `/v2/usage` (403, 사용량 차감 없음) |
| 새 연결 비용 | TCP 250ms + TLS 250ms = **약 510ms**, 요청 전체 783ms | 같은 방법 |
| 열린 연결 재사용 | 요청 전체 **249ms** | 한 `curl`에서 두 번 요청 |
| HTTP/2 | 지원 (ALPN `h2`). Qt 6은 기본으로 HTTP/2를 쓴다 | `openssl s_client -alpn` |
| 서버가 쉬는 연결을 닫는 시간 | 15초 뒤엔 살아 있음, 45초 뒤엔 닫힘 | 간격을 둔 두 요청의 새 연결 수 |
| DeepL 모델 선택 | 기본값이 이미 `latency_optimized`(가장 빠른 모델) | [DeepL API 문서](https://developers.deepl.com/docs/api-reference/translate) |
| 화면 캡처 비용 | 1200×300 영역 3.6ms, 1800×400 7.1ms | GDI 캡처 60회 평균 |

해석:
- 한국에서 유럽 서버로 가는 왕복 시간이 커서, **연결을 미리 열어 두는 것이 가장 큰 단일 이득**이다(최대 약 0.5초).
- 대사 사이가 15–45초 넘게 비면 연결이 닫힌다. 그래서 대사가 나타나는 순간 연결을 미리 연다. 이 준비 시간은 글자 출력이 멈추길 기다리는 시간과 겹친다.
- DeepL 쪽에서 더 빠른 모델을 고를 여지는 없다.
- 캡처는 싸서 0.15초마다 해도 CPU 부담이 작다. 6.7회/초 × 약 5ms = 한 코어의 약 3%, 이 PC 전체의 0.2% 미만이다.

## 3. 목표와 범위

목표: 대사가 멈춘 뒤 번역이 뜨기까지를 지금의 절반 이하로 줄인다. 번역 결과와 DeepL 사용량 규칙은 그대로 둔다.

| ID | 바꿀 것 | 기대 효과 |
|---|---|---|
| L1 | 변화 확인 0.4 → **0.15초**, 출력 멈춤 판단 0.8 → **0.3초**(같은 화면 2번) | 알아채기 −0.13초, 기다림 −0.5초 |
| L2 | 끝나지 않은 문장(마지막 글자가 `。！？.!?」』…` 등이 아님)은 지금처럼 0.8초 멈출 때까지 번역을 미룸. OCR은 먼저 해 둠 | 타자기 효과의 쉼표에서 문장 반쪽을 보내지 않음(사용량 그대로) |
| L3 | DeepL 연결 미리 열기: 대사가 나타날 때, 자동 번역·올려두기 시작, 단축키, 영역 선택 때. 15초 안에 쓴 연결이 있으면 생략 | 끊긴 연결 −0.5초 |
| L4 | 최근 번역 200줄을 메모리에 기억해 같은 원문은 DeepL 없이 바로 표시 (파일 저장 없음) | 반복 대사 0초, 사용량 감소 |
| L5 | 자막 창을 시작할 때 미리 만들어 둠 | 첫 표시 지연 제거 |

범위 밖과 그 이유:
- **연결을 살려 두려는 주기적 요청**: 키를 계속 보내는 트래픽이 생긴다. L3으로 충분하다.
- **다른 번역 서비스**: 사용자 본인 DeepL 키 원칙.
- **올려두기 1초 정지 줄이기**: 손이 지나가다 멈춘 것까지 번역해 사용량이 는다. 이번에는 L3만 붙인다.

### 정합성

| 원칙·결정 | 확인 |
|---|---|
| 필요한 만큼만 보낸다 | L2로 문장 반쪽은 지금처럼 보내지 않음. L4는 오히려 요청을 줄임. L3은 연결만 열고 요청·키는 보내지 않음 |
| 이미지·원문·번역을 파일로 저장하지 않음 | L4는 메모리에만, 앱을 닫으면 사라짐. 기획서 7.4 "직전 번역 1건"을 "최근 200줄"로 바꾸는 결정 기록 |
| 게임을 방해하지 않는다 | 캡처 0.15초 간격의 CPU를 측정해 기록 |
| 3초 넘게 출력되는 문장은 중간에 한 번 읽음(P-24) | 그대로 |
| DeepL 실제 호출은 확인 없이 하지 않음 | 연결 측정은 `/v2/usage`에 가짜 키(403)로, 사용량 차감 없음. 번역 캐시는 로컬 HTTP 테스트 서버로 검증 |

## 5. 결과

### 수정 전 / 후 (같은 PC, 2026-11-02)

| 측정 | 수정 전 | 수정 후 |
|---|---|---|
| **대사 바뀜 → 앱이 읽은 원문** (QA A-03/C-02, 가짜 게임 창 20줄, 키 없음) 중앙값 / p95 | 1,118 / 1,608ms | **480 / 810ms** |
| 놓친 대사 | 0 / 20 | 0 / 20 |
| **DeepL 요청, 연결이 끊긴 뒤** (앱의 `TranslationService`, 5회 중앙값) | 1,058ms | **252ms** (대사가 나타날 때 미리 연결) |
| DeepL 요청, 열린 연결 | 251ms | 251ms (그대로) |
| 최근 200줄 안의 같은 원문 | DeepL 요청 (직전 1줄만 기억) | **요청 없이 표시**, OCR 포함 102ms (테스트) |
| 끝나지 않은 문장 (`今日はいい天気`) | 0.8초 멈춘 뒤 전송 | 바로 읽고 0.8초 멈춘 뒤 한 번 전송 (테스트: 시작 후 1,142ms, 전송 1회) |
| 타자기 효과 부분 읽기 (20·28·40자 × 100ms, 40자 × 200ms) | 0 · 0 · 3 · 6 | 0 · 0 · 3 · 6 (같음) |
| 자동 번역 대기 CPU (QA C-03, 5분, 논리 프로세서 24개 기준) | — | 0.05% (목표 3% 이하), 메모리 174 → 174MB |
| CTest | 180 | **184 통과**, 실패 0, 건너뜀 0 |

수정 전 값은 같은 코드에서 대기 시간 상수만 예전 값(0.4초·0.8초)으로 바꾼 빌드로 쟀다. 대사 → 원문 측정은 키가 없는 QA 설정이라 번역 시간이 들어 있지 않다.

키가 있을 때 대사가 바뀐 뒤 번역이 화면에 뜨기까지는 다음과 같다(추정, DeepL 처리 시간 제외).
- 수정 전: 약 1.1초 + 0.25초, 연결이 끊겼으면 + 1.06초
- 수정 후: 약 0.48초 + 0.25초, 반복 대사는 0.1초

### 항목별 결과

- **L1**: 변화 감지를 0.4초 → 0.15초 간격으로, 대기를 "2번 연속"에서 시간 기준 0.3초로 바꿨다(`ChangeDetector::PollMs`, `SettleMs`). 테스트는 간격 상수로 다시 썼다.
- **L2**: 문장 끝이 아닌 줄은 OCR까지 마치고 기다린다.
  - 화면이 0.8초 그대로면 그때 보낸다. 그 사이 바뀌면 버리고 새 줄을 읽는다.
  - `looksFinished`: `。．.！!？?…‥」』）)】〉》"”’'～~♪`로 끝나면 끝난 문장으로 본다.
- **L3**: `TranslationService::warmUp`은 요청 없이 TLS 연결만 연다(ALPN h2). 15초 안에 쓴 연결이 있으면 생략한다.
  - 호출 시점: 대사가 나타난 순간, 자동 번역·올려두기 시작, 마우스가 멈춘 순간, 단축키 캡처, 영역 선택.
  - 키와 전송 동의가 있을 때만 연다.
- **L4**: 대상 언어·원문 언어·조각으로 만든 키로 최근 200줄을 메모리에 기억한다(앱을 닫으면 사라짐). 상태 문구에 "(기억해 둔 번역)"이 붙는다.
- **L5**: 자막 창의 네이티브 창을 시작할 때 만든다.
- **QA 하네스**: P-30에서 OCR 원문 칸이 별도 창으로 옮겨져 하네스가 원문을 읽지 못했다.
  - 메인 창 자막 무대의 접근성 이름("마지막 대사: 원문 / 번역")을 읽게 했다.
  - 화면 읽기 프로그램도 이 이름으로 마지막 대사를 읽는다.

### 개발 중 발견한 것

- **빌드 스크립트가 바뀐 헤더를 놓칠 수 있음**: `build-windows.ps1`의 `Copy-Item`은 파일의 수정 시각을 그대로 복사한다. 그래서 저장소의 헤더가 이미 컴파일된 결과물보다 오래된 시각이면 다시 컴파일하지 않는다. 비교 빌드에서 "수정본"이 예전 상수로 만들어져, 두 빌드가 같은 1.1초로 나왔다. 헤더의 시각을 갱신해 다시 빌드한 뒤 480ms를 확인했다. → P-32
- **빌드 출력을 잘라 읽으면 빌드가 끝나지 않는다**: PowerShell에서 `cmake --build ... | Select-Object -First N`을 쓰면 줄 수가 차는 순간 파이프가 닫혀 빌드가 중간에 멈춘다. 그 결과 테스트 실행 파일이 새 라이브러리로 다시 링크되지 않아 CTest가 8개 실패했다. 출력은 파일로 받고, 다시 링크된 시각을 확인한 뒤 184개 통과를 확인했다.
- **Qt 연결 첫 요청은 curl보다 느리다**: 같은 서버에 1,058ms 대 783ms. TLS와 HTTP/2 설정 왕복이 더 있다. 그래서 미리 연결의 이득이 예상(0.5초)보다 큰 0.8초였다.
- **같은 연결을 쉬지 않고 바로 다시 쓰면 538ms**: 응답 직후 곧바로 요청한 경우다. 1초 뒤에는 251ms였다. 앱은 대사 사이에 시간이 있어 영향이 없다.
- **QA 설정은 키·동의를 끈다**: `Use-QaBaseSettings`가 `consent=false`, `rememberKey=false`로 덮어써서 측정 중 DeepL 호출은 없었다.

### 아직 확인하지 못한 것

- **실제 번역 요청의 DeepL 처리 시간**: 사용량이 차감되어 재지 않았다. 왕복 0.25초에 서버 처리 시간이 더해진다.
- **실제 게임의 타자기 효과**: 쉼표 뒤에 0.3초 넘게 멈추는 게임에서 L2가 반쪽 문장을 막는지 → P-13.
- **논리 프로세서가 적은 PC의 0.15초 캡처 부담**.
