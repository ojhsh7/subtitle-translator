# OCR 인식 속도 개선과 구현 언어·엔진 탐색 — 계획과 결과

작성 2026-11-01 · 백로그 P-26 · 브랜치 `ocr-accuracy-foreign-only` · 기준 커밋 `63e6a8b`

요청: "인식 속도를 빠르게. 언어는 상관없으니 이 프로젝트에 가장 맞는 언어를 탐색하고, 가장 좋은 방안을 모순 없이 계획한 뒤 만든다."

결론 먼저:
- **구현 언어는 C++를 유지한다.** OCR 시간의 93–98%가 ONNX Runtime 내부 계산이고, 우리 코드는 2–7%뿐이다. 어떤 언어로 다시 써도 같은 ONNX Runtime을 부르므로 빨라질 몫이 없다.
- **엔진은 PaddleOCR(ONNX Runtime, CPU)을 유지한다.** Windows 내장 OCR은 4–19배 빠르지만 오류율이 14–58배 높다.
- **속도는 세 군데에서 얻는다.** 스레드 1 → 최대 4, 모델 미리 불러오기, 앱 창이 영역을 가리지 않을 때 캡처 전 180ms 대기 없애기. 인식 결과는 840장 모두 그대로다.
- **결과**: 단축키 → 화면 자막 중앙값 351 → **83ms**, 기본 설정 대사창 OCR 288 → **105ms**, 한 줄 44 → **18ms**. CTest 174 통과, 건너뜀 0 (6절).

## 2. 언어·엔진 탐색

### 2.1 시간은 어디에 쓰이나

| 측정 (대사창 168장, 스레드 1) | 값 |
|---|---|
| 전체 OCR 시간 중 ONNX Runtime `Run` 안 | **97.4%** (스레드 4: 94.4%, 스레드 8: 93.0%) |
| 검출·인식 단계 밖(단색 검사, 결과 정리) | 0.2–0.7% |
| 한 줄 672장에서 ONNX Runtime 비율 | 97.4% (스레드 4: 93.9%) |

ONNX Runtime의 계산 커널(MLAS)은 C++로 쓰여 있고, 다른 언어의 바인딩도 같은 C API로 이 커널을 부른다. 그래서 언어를 바꿔 줄일 수 있는 시간은 우리 코드 몫인 2–7%(대사창 기준 2–5ms) 안이다.

### 2.2 구현 언어 비교

| 후보 | 핵심 경로 속도 | Windows 캡처·오버레이·단축키 | Android와 코어 공유 | ONNX Runtime | 전환 비용 | 판단 |
|---|---|---|---|---|---|---|
| **C++17 (현재)** | ONNX Runtime C++ API 직접 호출, 우리 코드 2–7% | Win32·Qt 직접 | 공통 코어를 JNI로 이미 공유 | 공식 | 없음 | **유지** |
| Rust | 같은 ONNX Runtime (`ort` 바인딩). 이득은 2–7% 안 | `windows-rs`로 가능하나 Qt UI를 다시 만들어야 함 | JNI로 가능 | 커뮤니티 바인딩 | 4,163줄 + 테스트 174개 재작성, UI 재설계 | 메모리 안전성 외 이득 없음 |
| C# (.NET) | 같은 ONNX Runtime + GC 일시 정지 | WPF·WinUI 좋음 | 공통 코어 공유 불가 (Android는 따로) | 공식 | 전체 재작성 | 이득 없음 |
| Python | 이미지 전처리·후처리가 느려짐(지금 2–7% 몫이 커짐), 시작 느림 | 가능 | 불가 | 공식 | 전체 재작성, 배포 크기 증가 | 부적합 |
| Kotlin/Java | Android 전용 | Windows 부적합 | — | — | — | 부적합 |

C++가 최적인 이유는 속도가 같아서만이 아니다. Windows API를 직접 쓰고, Android와 공통 코어를 이미 공유하며([결정 2026-09-29](DECISIONS.md)), 측정 도구와 테스트 174개가 그대로 남는다.

### 2.2.1 AI 개발 비용 (토큰 사용량)

이 프로젝트는 AI(Claude Code)로 개발하므로, 언어마다 작업량이 토큰 사용량으로 이어진다. 아래 "변경 1건당"은 [추정]이다. 다만 C++ 칸의 원인은 이 저장소에서 실제로 겪은 일이다.

| 후보 | 변경 1건당 | 주된 원인 | 전환 1회 비용 |
|---|---|---|---|
| **C++ (현재)** | 중간–높음 | 헤더·구현 두 파일을 읽고 고침. MSVC·Qt 함정으로 빌드를 다시 돌림(`windows.h`의 `max`·`near` 매크로, moc가 원시 문자열을 못 읽음, 2026-10-25). 빌드 출력이 김 | 없음 |
| Rust | 중간–높음 | 빌림 검사 오류를 고치느라 반복이 생김. Qt 대체 UI 자료가 적음 | 매우 큼: 코드 4,163줄·테스트 174개 재작성, UI 재설계, 측정 전부 다시 |
| C# | 낮음 | 오류 메시지가 명확하고 빌드가 빠름 | 매우 큼 + Android 공통 코어 포기 |
| Python | 낮음 | 짧은 코드, 빌드 없음 | 매우 큼 + 성능·배포 문제(위 표) |

새로 만든다면 C#이 토큰을 가장 적게 쓸 수 있다. 하지만 이 프로젝트에서는 전환 1회 비용이 변경마다 아끼는 몫보다 훨씬 크다. 남은 일(P-12·13·22·23·27 등)은 대부분 측정·검증이라 언어와 관계없이 드는 토큰이다. 그래서 **토큰 기준으로도 C++ 유지가 가장 싸다** [추정].

C++에서 토큰을 줄이는 방법은 언어를 바꾸지 않고도 쓸 수 있다.
- 빌드·테스트 출력은 요약 줄(오류, `Totals`)만 본다.
- 큰 파일(`main_window.cpp` 1,238줄)은 필요한 부분만 읽는다.
- 이미 겪은 MSVC·Qt 함정은 이 절과 결정 기록에 남겨 같은 실수를 반복하지 않는다.

### 항목별 결과

- **S1 공용 스레드 풀**: 모델마다 있던 스레드 설정을 없애고 프로세스 하나에 풀 하나(이 PC 4개)를 둔다. 쉬는 스레드는 잠든다(spin 0). 스레드 수에 따라 결과가 바뀐 이미지는 없다(1·2·4·8 모두 같음). 테스트 `defaultThreadsLeaveTheGameMostOfTheCpu`.
- **S2 미리 불러오기**: 앱 시작, 설정 저장, 원문 언어 변경 때 백그라운드로 검출 모델과 첫 단계 인식 모델을 불러와 한 번 실행한다. 다국어 설정은 1단계 모델 2개만 불러온다. `paddle_tests` 측정으로 첫 읽기 226 → 23ms. 테스트 `warmUpLoadsTheModelsBeforeTheFirstRead`(읽기 결과가 같은지, 첫 읽기가 빨라졌는지, Tesseract 엔진 설정에서도 동작하는지).
- **S3 캡처 대기**: 앱 창이 영역 밖이면 숨기지 않고 바로 캡처한다. 메인 창이 단축키마다 깜박이던 것도 사라진다. 영역과 겹치면 예전처럼 숨기고 180ms 기다린 뒤 다시 보인다. 테스트 `captureHidesOnlyWindowsInThePicture`(두 경우 모두 원문을 바르게 읽음).
- **G1 진단**: 벤치마크 결과 v3에 검출·인식 시간과 ONNX Runtime 시간, `--threads`, `--warm-up`.

### 개발 중 발견한 것

- 여러 줄을 한 번에 인식하는 배치는 PaddleOCR 공식 구현의 방식이지만 이 모델·CPU에서는 더 느렸다. 가장 넓은 줄에 맞춰 덧붙인 빈칸이 계산량을 늘리고, 그 빈칸 때문에 34장의 결과가 바뀌었다. 구현했다가 측정 후 뺐다.
- Windows 내장 OCR은 한 줄 이미지(높이 34px 안팎)를 거의 읽지 못했다(CER 59–69%). 작은 게임 글씨에는 맞지 않는다.
- 설치본이 실행 중이면 창 닫기 요청으로 끝나지 않았다(숨은 창). UI 테스트 전에는 프로세스를 종료해야 한다. [PROJECT.md](../../PROJECT.md) 안전 규칙과 같다.

### 아직 확인하지 못한 것

- 실제 게임을 실행한 상태에서 읽기 순간 스레드 4개가 게임 프레임에 주는 영향 → P-13.
- 논리 프로세서가 적은 PC(4–8개, 스레드 1–2개)의 속도. 이 PC에서 스레드 2개는 대사창 105ms였다.
- 시작 직후 메모리. 미리 불러오기로 모델이 첫 읽기 대신 시작 때 올라간다 → P-12에서 함께 잰다.
