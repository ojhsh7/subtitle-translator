# 자동 번역 중 메모리 줄이기 — 계획과 결과

작성·완료 2026-11-23 · 백로그 P-43 · 브랜치 `ocr-accuracy-foreign-only` · 기준 커밋 `a0f6a35`

요청: "남은 것도 계속 개선하며 개발." 남은 항목 중 이 PC에서 할 수 있는 것을 골랐다(나머지는 실제 게임·모니터 2대·실기기·인증서 구매가 필요).

## 1. 문제

설치본 앱은 대기 상태에서 private 81MB지만, 자동 번역 중에는 약 400~460MB를 썼다(P-12 1시간 측정 400~403MB, 장면 측정 436~460MB). 게임과 함께 켜 두는 도구라 줄이면 체감이 있다.

처음 시도(같은 날 앞서)에서는 ONNX Runtime 설정을 바꿔도 차이가 없었다. 측정 도구가 실험 코드를 넣기 전의 실행 파일로 돌았던 것으로 보인다(빌드 도중 측정을 멈췄다). 이번에는 단계별로 다시 쟀다.

## 2. 측정

### 2.1 어디서 늘어나나 (OCR 엔진만, `expression_probe`)

| 설정 | 시작 | 모델 불러온 뒤 | 1100×220 읽은 뒤 | 1920×400 읽은 뒤 | 256번 읽은 뒤 |
|---|---|---|---|---|---|
| 기본(지금) | 59MB | 151 | 328 | 461 | **495** |
| 아레나 끄기 | 59 | 121 | 126 | 127 | **160** |
| 가중치 미리 변환 끄기 | 59 | 185 | 361 | 494 | 528 |
| 최적화 단계 BASIC / EXTENDED | 59 | 149 / 151 | 326 | 459 | 493 |
| 아레나·패턴·미리 변환 모두 끄기 | 59 | 121 | 128 | 123 | 162 |
| 읽은 뒤 아레나 줄이기 | 59 | 131 | 161 | 158 | **187** |

모델 자체는 약 90MB이고, 나머지 300MB 넘게는 **ONNX Runtime의 메모리 아레나가 읽기마다 받은 작업 메모리를 놓지 않아서**였다. 가장 큰 그림을 읽은 만큼 남는다.

### 2.2 앱에서 메모리와 속도 (`scene_probe`, 장면 4개 × 2번)

| 설정 | 자동 번역 중 메모리 | 한 번 읽기(장면 평균) | 요청 = 줄 |
|---|---|---|---|
| 기본(지금) | 436~460MB | 47~78ms | 예(한 번 5/4) |
| 아레나 끄기 | 146~161MB | 62~97ms (**+10~20ms**) | 예 |
| **읽은 뒤 아레나 줄이기** | **171~184MB** | 52~84ms (**+0~7ms**) | 예 |

자막이 뜨기까지의 시간은 세 설정 모두 오차 안이다(0.4~0.6초, 대부분은 멈춤 판단과 번역 대기).

## 3. 결정과 변경

**읽은 뒤 아레나 줄이기**를 쓴다(ONNX Runtime 실행 옵션 `memory.enable_memory_arena_shrinkage = cpu:0`). 메모리는 약 60%(약 270MB) 줄고 읽기는 몇 ms만 늘어난다. 아레나를 아예 끄면 메모리는 조금 더 줄지만 읽기가 10~20ms 느려진다.

- `PaddleOcr`의 모든 실행(취소할 수 있는 읽기, 모델 미리 불러오기 포함)에 적용(`giveBackMemory`).
- 측정 도구 `expression_probe`가 단계별 메모리를 출력한다.
- 테스트 `largeReadGivesItsMemoryBack`: 모델을 불러온 뒤 1920×400 그림을 세 번 읽어도 메모리가 100MB 넘게 늘지 않는다(측정 +49MB, 고치기 전 약 +310MB).
